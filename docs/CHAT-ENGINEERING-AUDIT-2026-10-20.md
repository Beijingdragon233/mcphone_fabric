# 美西螈工程性与边界审查（2026-10-20，10-22 复核）

## 审查结论与范围

本次审查基于 `codex/chat-replies`，已快进接入 `main` 的 `cd1a9ece`（PR #72）。重点逐行检查引用回复的数据模型、两代编解码、四个平台接线、私聊和群聊权限、提交确认、输入草稿与排版；同时抽查收藏存储、图片缓存/上传、断线入口、公开聊天 API 和构建闸门。不是对整个仓库每条运行路径的形式化证明。

现有 shared → version/loader/platform 分层可以继续维护，无需为追求文件数量再次搬动工程目录。审查确实发现了会影响后续功能的缺陷，已修复并补回归；下面区分已解决问题与仍需投入的维护事项。游戏内视觉、真实多人延迟及各类第三方资源包仍需实测，不据编译结果宣称验收完成。

## 已修复的具体问题

| 风险 | 触发与影响 | 修复与证据 |
| --- | --- | --- |
| 旧消息身份随模型演进漂移 | 迁移种子使用 `MessageBody.toString()`；TextBody 增加 quote 后，即使为空也改变字符串。旧聊天未回存、删除标记先回存时，重载可能失去删除对应关系 | 冻结 1.11.2 文本和图片迁移字符串。`ChatReplyIdentityTest` 使用固定 UUID 金样，实际重载删除数据验证，不从新 toString 推导预期 |
| 相同正文误确认、超时重发重复落库 | 原来以“正文＋原消息＋不在旧集合”匹配回声，迟到的第一次回复可能确认第二次；重试随机生成新消息 | 新增 `ChatReplyIdentity`。独立票据绑定真实作者、会话和群/私聊域；服务端从票据生成消息 ID，核对已存正文与引用目标。同一提交重试不追加，也不重复通知对方 |
| 等待确认时误清草稿 | 原来清洗当前输入再比较，增删空格也会当成原正文；编辑后改回也不能识别 | Composer 保存原始正文和编辑次数；只清理精确原快照。超时保留票据和正文，使用单调时钟。Submission/Layout 测试覆盖改空格、编辑后撤销和迟到确认 |
| 私聊重试出现两个气泡 | 服务端补发相同消息 ID 后，客户端原来无条件追加 | ChatClientCache 按消息 ID 去重，保持快照引用；仍调用监听器处理提交/上传确认。缓存回归覆盖此行为 |
| 群聊只等正文回声，无法明确确认重试 | 群推送只有最后一条摘要，已存旧提交不能作为新消息再次广播；服务端错误已有统一提示 | 复用 GroupCommand.request 作提交票据。首次通过原消息推送确认，去重重试只返回 Result；满容量重试已有票据不挤掉其他请求；缓存记录被跟踪的确认，页面恢复操作，错误继续由 GroupTransport 提示一次 |
| 损坏快照引发构造异常 | 无界字符串 Codec 先解码，再在 record 构造器抛异常 | 字段 Codec 使用 DFU 6/8/9 共通的双向校验；可选引用显式区分缺失与损坏，绕过 DFU 6 会吞错的默认 optionalFieldOf。返回 DataResult 错误，Codec 测试在两代库上覆盖 |
| Fabric 改名后旧端识别失效 | 用刚改名的摘要通道判断旧客户端是否装了 MCPhone，会漏掉旧端；新客户端连旧服也缺明确检查 | 服务端改用未变化的在线玩家通道识别，再检查所有新增正文通道；客户端检查服务端新的发送和群请求通道。Forge/NeoForge 同步推进注册版本 |
| 图片缓存元数据无限累积 | 仅以像素字节限制；LOADING/GONE/BROKEN 可能为零字节，跨大量会话后仍增长 | 在原字节限制外增加 256 条元数据上限，各入口执行 LRU；被逐出或同 ID 重建后的后台解码结果关闭像素并丢弃，不接管新条目。实际缓存无 GL 测试连续写入 2000 个 ID |
| 引用摘要拼接换行词语 | 单行清洗直接去掉换行，可能把原来两行单词连成一个 | 摘要生成先将换行换成空格，再统一清洗和限长；不改变正文的选择与复制语义 |

## 工程边界与硬编码检查

- 引用快照与身份规则在共享数据层；服务端不采信客户端名字、作者、时间或摘要，只接收原消息 ID 和票据，并重新检查好友/群成员、本人可见性及入群历史边界。
- UI 分为引用草稿、提交状态、摘要视图；会话页协调生命周期，Channel 区分私聊/群聊，并将提交结果投影为统一状态；会话页不依赖群错误枚举。Composer 不持有 peer、网络包或群业务。菜单只回调不可变消息身份，不读取页面全局状态。
- 私聊四个平台复用 ChatDelivery 的文本提交协调；重复确认只补发给发送者。群聊继续由 GroupService/GroupServer 分担业务和推送，不把平台分支塞进 shared。
- `ChatQuote.TEXT_LIMIT` 引用 `TextBody.MAX_LENGTH`，没有重复散落 256 字符上限；服务端消息/群缓存继续保留 100 条。6000ms 是引用确认策略，集中在 Submission；256 条与 24MiB 是图片缓存策略。固定协议版本和旧 ID 种子是兼容契约，不能改成随配置变化的值。
- 圆环左引号使用 Lucide 固定版本的原始 SVG，保留上游许可、组合 SVG 和重建脚本；运行包仍只用 PNG。没有依赖用户机器绝对路径、远程图标 CDN 或未固定的运行时下载。
- `TextBody(String)`、普通发送与原公开聊天 API 入口保留；未让 API、存档或网络依赖客户端类。引用快照存档字段为可选，普通文本仍写旧格式。
- 接缝清单与平台孪生基线通过任务生成后逐项检查。差异增量只涉及 TextBody、SendChatMessagePacket 两代 codec，以及 Fabric 专属协议检查；没有手改数值绕过闸门。

| 优先级 | 现状 | 何时应处理 |

| 中 | ChatImageSender 约 500 行，涉及压缩、动图、排队和上传；目前有票据、连接与容量保护 | 扩展视频/文件前拆编码策略与上传协调，并补服务器实际异步写入/清理交错测试 |
| 中 | 收藏同步写本地文件，虽然有原子替换、2MiB/512 条上限和失败保留快照，慢盘仍可能短暂卡帧 | 如果加入图片收藏或大量导入，改成单线程顺序写入＋带世代确认，避免直接 fire-and-forget |
| 中 | 引用去重依赖保留的 100 条消息，不是永久事务日志；客户端关闭会话不持久保留未确认票据 | 若要离线可靠投递/重连自动补发，应设计持久 outbox 与有界服务端提交日志，而不是延长当前 6 秒超时 |
| 中 | 私聊历史协议目前靠主线程与有序传输保持快照顺序，没有群聊那样显式序号 | 将来引入后台数据库或分页时，应先增加请求票据/快照版本，不直接异步化现有历史回包 |
| 低 | 图片字节上限保留至少 4 条，属于避免当前屏幕抖动的软上限；真实显存还包括驱动开销 | 更大素材格式或低显存目标要做实测预算；条数上限不能代替显存统计 |
| 低 | 头像离线缓存仍仅在当前客户端会话内，字体光学居中按当前字体度量 | 持久头像与第三方字体分别做独立设计，不在引用 PR 中混入 |
| 测试债务 | Windows EconomyDataTest 假定 POSIX 文件系统 | 另开跨平台测试修复；此 PR 保留测试并依靠 Linux 完整 CI |

引用是独立转述快照：删除原消息不追删其他人的引用；有权读旧消息的成员可以把摘要转述给当前群成员。这是当前产品语义，不等于授予新成员读取旧图片或旧历史的权限。降级版本可能忽略引用元数据并在重存时丢失它，升级前仍应保留存档备份。
