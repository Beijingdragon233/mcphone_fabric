# S16 核实记录：签名与信任

> 这是一份核实记录，不是设计。**施工方案本身不在本仓库里**，文中的 §编号指它。

对应 §12.1–§12.9、勘误 E21 / E22。日期 2026-09-17，分支 `feature/script-sign`。

## 一、签名不防病毒 —— 这条要先说

它只证明"这份字节是这个密钥签的"。挡住毒的是 §3.4 的包内容白名单
（`.class` / `.jar` / `.so` / `.exe` … 一律拒绝整包，经典意义的病毒结构上不可能）与 §16 的沙箱。

**任何文案里都不许出现"已签名 = 安全"。** `INSTALL_NOTE` 每次安装都显示，
就是为了把这个区分讲给玩家，而不是让他以为绿色等于无害。

## 二、Ed25519 本轮实测（JDK 17，1.20.1 那一支的目标版本）

```
公钥 X.509 44 字节 / 私钥 PKCS8 48 字节 / 签名 64 字节
验签 true；改一字节 false
```

§12.2 那处"⚠ 待核实：1.20.1 分支的 Java 目标要 ≥ 15"可以关掉了 —— 实测就是 17。

## 三、三个域分隔符，互相不能当输入

| 用途 | 域 |
|---|---|
| 包摘要（§3.3，S1 已有） | `mcphone-pkg-v1\0` |
| 包签名（§12.3） | `mcphone-sig-v1\0` |
| 轮换声明（§12.6） | `mcphone-rotate-v1\0` |

断言里两个方向都试了：用轮换的域签出来的签名，在包签名这边验不过；反过来也不行。

## 四、META/ 白名单：E22 的裁定落地

§12.3 写"除 sig.json 外任何文件即拒绝"，§12.6 又要求把轮换声明放 `META/rotate.json` ——
两条直接打架，而 `PackageReader` 现在正照 §12.3 抛 `E_PKG_META_EXTRA`。

裁定：**封闭列举 `{sig.json, rotate.json}`，两者都不进摘要、都必须自带签名。**
S1 的"摘 META/ 目录 + 白名单"逻辑没有重做，只把单值扩成两个具名常量。

断言里钉住了三条：sig.json 内容变了摘要不变、多一个 rotate.json 摘要也不变、
META/ 下出现第三个文件整包拒绝。

## 五、四档判定是纯函数

`TrustState.of(包, appId, 信任库) → Verdict`。**UI 只渲染，不再判一遍** ——
两份判据迟早对不上，那种不一致的表现是"界面说能装，装下去被拒"，或者更糟，反过来。

**硬拒绝只有「签名无效」一档。** 把「未签名」也做成硬拒绝会逼所有人去找绕过办法，
而未签名的包并不比签名的更危险。断言里数了一遍：五档里 `installable == false` 的正好一个。

**`alg` 不认识 → 「签名无效」，不是「未签名」。** 那会把硬拒绝降级成二次确认。

## 六、轮换：旧公钥从信任库取，不是从包里取

从包里取等于让声明自己证明自己 —— 任何人都能塞一个"我换钥匙了"，把自己的公钥接到别人的信任上，
TOFU 整个作废。所以 `applyRotation` 的前提是**旧指纹已经被信任**，且用**库里存的**旧公钥验过。

断言里试了冒名者签的声明：拒绝，且旧指纹没被记过时也拒绝。

### 那三样为什么没做

不是漏了。它们是**界面与构建脚本**，而这一步真正难的部分（密码学、判定、白名单裁定、轮换）
已经全部落地并有断言。三样各自的理由：

- **安装界面**：要在 `AppDetail` 上加四档配色、确认短语输入框、INSTALL_NOTE 段落 ——
  §12.9 里那几条判据（"INSTALL_NOTE 真的显示"、"没有暗示内容安全的图标"）
  **只能在 runClient 上验**，我写完也没法确认对不对。
- **`gradlew signApp`**：要动构建脚本，而它与 `verifyPlatformTwins` / CI 的交互我没法本地跑全。
- **开发者密钥界面**：同上，且它要展示"此文件未受系统级保护"这类平台相关状态。

密码学那一侧已经准备好：`AuthorKeys.buildSigJson(...)` 就是「打包并签名」要调的那一个，
两条路径（界面按钮 / gradle 任务）调它即可。

**安装路径上「签名无效」这一档已经生效**：`LocalScriptSource` 在装之前判一次，
无效就拒绝并给出文案键 —— 那是唯一的硬拒绝，不能等界面。
